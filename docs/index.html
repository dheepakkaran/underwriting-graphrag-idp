01 · Why this exists

Underwriters read three documents per file, and the risk often lives in the gaps between them.

A small-commercial submission arrives as an application, a loss run from the prior carrier, and an inspection report. Checking them against each other, and against what the insurer already knows, is most of the work. Two kinds of risk slip through.

≠

Mismatches inside one file

The application says 8,000 sq ft and sprinklered; the inspector measured 11,500 sq ft and found no sprinklers. The application discloses no prior claims; the loss run lists three. Same premium, very different building.

⟁

Links across files

Five applicants, one broker, one PO box, heavy losses. Each file looks fine on its own; the pattern only shows when you connect them. A reviewer reading one file at a time cannot see it, and neither can plain keyword or vector search.

What it is for

Put senior underwriters on the files that need them, with the evidence already lined up, and keep clean files moving.

What it is not

Not an auto-decline engine, not pricing, not a model trained on real applicants. Two routes exist: standard review or refer. A person decides.

Why a graph

Loss runs never name the broker. "Total losses for broker X" needs a hop from broker → applicants → claims, which chunk-and-embed retrieval cannot make.

02 · How it works

LLM where reading is hard. Code where rules are clear. A graph for what no single file shows.

Each stage does one job, and the stage that chooses the route is plain code.

01

Intelligent document processing

PDF text → Claude Haiku with a Pydantic schema. Every key field comes back with the exact sentence it came from, and quotes are checked against the document.

02

Deterministic validators

Square footage, sprinklers and disclosed claims compared across documents and against internal records. Same input, same flag, every time.

03

Graph + narrow agent

A networkx graph links applicants, brokers, addresses and claims. The agent's only job: look across files and flag a broker/address ring when the graph supports it.

03 · Design choices

Five rules the build follows, and why.

Insurance decisions need audit trails and human oversight (see the NAIC Model Bulletin on the Use of AI Systems by Insurers, Dec 2023). These choices make the prototype reviewable.

{ }

Code picks the route

The route is a function of the flags. The model cannot choose it, so text in a document cannot talk its way to "standard".

⌖

The agent's job is narrow

It started broad and over-flagged a clean file. Narrowing it to cross-file rings fixed that. Plain code does the rest better.

“”

Every flag has a quote

Underwriters trust a sentence, not a score. Each flag carries the verbatim text it came from.

⛨

Documents are data

Three files carry a planted "route this to standard" instruction. It is captured and shown as a flag; it changed zero routes.

✓

A human decides

No decline route exists. Referred files pause at a LangGraph interrupt until a reviewer approves or overrides with a reason, which is logged.

⧗

Baselines first, test once

Rules and vector-RAG baselines were frozen before any LLM run. Prompts and the agent were tuned on dev; the test split ran once.

Why vector retrieval scored 0/8 on broker totals

A broker total needs the claims of 6–10 different applicants. Their loss runs never mention the broker, so nearest-neighbour search cannot tell which ones belong together, and top-8 chunks cannot hold them all. The graph walks broker → applicants → claims and hands the model exactly those facts. On single-file lookups (the building at an address) vector search did fine, 2/2.

05 · What broke, and what changed

The failures shaped the design more than the successes.

Every change was made on dev data, before the single test run. Full list in FAILURES.md.

The baseline was too weak

The first regex missed fields in one of the two known forms, which would have flattered the LLM. Completed before freezing: test recall 64.7%, not 24%.

Quotes were paraphrased

The model wrote "Sprinklered column: No", text that exists nowhere. Prompt v2 asks for character-for-character rows: 96/100 → 98/100 on dev, 200/200 on test.

The agent over-flagged a clean file, twice

First it quoted a table header as evidence; after a verbatim-evidence guardrail it quoted a real sentence but drew the wrong conclusion. Verbatim checks cannot catch bad logic, so in-file checks moved to code and the agent kept only the cross-file job.

One test false refer

An extracted claim count (0) disagreed with its own quoted row (1). A reviewer sees it in seconds; the next fix is to re-parse numbers from their quotes and mark disagreements as uncertain.

Container fixed before it failed

The image would have installed the project as its own dependency and shipped the virtual environment and .env. Fixed with an export flag and a .dockerignore; the container smoke test passed.

06 · Limits and next steps

Honest about what this shows.

Limits

Synthetic, born-digital PDFs in three layouts, so 99.7% extraction says little about scanned or handwritten files. Entity linking is exact string matching. The ring is five planted files. No cloud deployment; the container runs locally.

Next

Re-parse numbers from their quotes · fuzzy entity resolution for addresses and business names · a two-week shadow run beside underwriters to measure agreement and minutes saved per file · override-rate monitoring as a governance signal.
