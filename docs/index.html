01 — Problem

Underwriters read three documents per file. The risk often sits between them.

A small commercial property submission arrives as an application, a loss run from the prior carrier, and an inspection report. Lining them up against each other, and against what the insurer already knows, is most of the work on a file. Two kinds of risk slip through.

Mismatches inside one file

The application says 8,000 square feet and sprinklered; the inspector measured 11,500 and found no sprinklers. The application discloses no prior claims; the loss run lists three.

Links across files

Five applicants share one broker and one PO box, and together carry heavy losses. Each file looks fine alone. The pattern only appears when the files are connected.

What it is for

Putting senior underwriters on the files that need them, with the evidence already lined up.

What it is not

An auto-decline engine. There are two routes, standard review or refer, and a person decides every file.

Why a graph

Loss runs never name the broker. Totals per broker need a hop from broker to applicants to claims.

02 — Approach

A language model where reading is hard, plain code where rules are clear, and a graph for what no single file shows.

  1. Document processing

    PDF text goes to Claude Haiku with a typed schema. Each key field returns with the exact sentence it came from, and every quote is checked against the document.

  2. Deterministic validators

    Square footage, sprinkler status and disclosed claims are compared across the three documents and against internal records. Same input, same flag.

  3. Entity graph and a narrow agent

    Applicants, brokers, addresses and claims form a graph. The agent's only job is to look across files and flag a broker and address ring when the graph supports it.

  4. Route in code, decision by a person

    The route is computed from the flags. Referred files pause at a LangGraph interrupt until a reviewer approves or overrides with a reason, which is logged.

Every flag has a quote

Reviewers trust a sentence more than a score.

Documents are data

Planted "approve this" instructions are captured as flags and changed no routes.

Baselines first, test once

Baselines were frozen before any model call; tuning used development data only.

Why vector retrieval missed broker totals

A broker total needs the claims of six to ten applicants. Their loss runs never mention the broker, so similarity search cannot tell which ones belong together. The graph walks from broker to applicants to claims and passes the model exactly those facts.

Where the cost went

Agent $0.050 · extraction $0.042 · retrieval $0.015. A hard $0.50 cap is enforced in code.

04 — Lessons

What broke, and what changed because of it.

  1. The first baseline was too weak

    A regex missed fields in one of the two known forms, which would have flattered the model. It was completed before freezing.

  2. Quotes were paraphrased

    The model wrote text that exists in no document. A stricter prompt raised verbatim quotes to 200 of 200 on test.

  3. A broad agent over-flagged a clean file, twice

    A verbatim-evidence check stopped invented quotes but not wrong conclusions. In-file checks moved to code and the agent kept only the cross-file task.

  4. One false refer remains

    An extracted number disagreed with its own quote. Next: re-read numbers from their quotes and mark disagreements as uncertain rather than risky.

Limits

Synthetic, born-digital PDFs in three layouts; the extraction score says little about scanned files. Entity matching is exact. The ring is five planted files. The container runs locally.

Next

Number re-checks against quotes, fuzzy matching for addresses and business names, and a two-week shadow run beside underwriters to measure agreement and time saved per file.
